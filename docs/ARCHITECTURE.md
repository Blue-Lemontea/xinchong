# 技术架构

> 用一句话概括：**桌宠 = 一个"透明、置顶、可点击穿透"的窗口 + 里面循环播放的动画 + 一个决定"现在播什么"的状态机。**

---

## 一、先看三个开源项目，各学一件事

| 项目 | 是什么 | 我们能学什么 |
|---|---|---|
| [BongoCat](https://github.com/ayangweb/BongoCat) | Electron 系的桌面猫，Live2D 模型，眼睛跟着鼠标动，按键有反应 | **验证了整套形态可行**：透明窗口 + 模型 + 事件驱动，离线不联网。它的「自带模型」思路正好对应我们的「换肤」 |
| [Shimeji](https://github.com/topics/shimeji-ee) | 经典的 Java 桌宠，精灵图 + 行为定义 | **行为状态机**的鼻祖。它证明「动画 + 状态 + 配置」三件套足够做出一只活物，不需要 AI |
| [DSHpet](https://github.com/lxtCuSO4/DSHpet) | 支持自定义角色的桌宠，透明动画、点击拖拽、多宠物 | **配置化素材**的做法：角色、动作、参数都写成配置，程序只负责播 |

三者的共同点：**没有一个是"靠 AI 聊天"撑起来的**，全都靠「动画 + 反馈」制造生命感。这和我们调研的结论完全一致（用户要的是「好看 + 解压」，不是「能聊」）。

## 二、进程模型

Electron 天生分两个进程，正好对应「身体」和「大脑」：

```
┌──────────────────────────────────────────────┐
│  主进程（Node.js，没有界面）                   │
│  · 创建/移动窗口                              │
│  · 托盘图标与右键菜单                          │
│  · 开机自启（写注册表）                         │
│  · 读写设置文件                                │
│  · 单实例锁（防止开两只）                       │
└──────────────────┬───────────────────────────┘
                   │  IPC（只通过 preload 暴露的白名单方法）
┌──────────────────┴───────────────────────────┐
│  渲染进程（一个透明的网页）                     │
│  · 宠物动画播放（Canvas / Live2D / 精灵图）     │
│  · 状态机（待机 / 点击 / 拖拽 / 睡觉）          │
│  · 台词气泡                                    │
│  · 音效播放                                    │
└──────────────────────────────────────────────┘
```

**为什么要分？**
窗口能不能置顶、能不能穿透、托盘怎么画——这些是操作系统的事，只能主进程干。
动画怎么动、台词说什么——这些是画面的事，在渲染进程里干最快。
两边用 IPC 通信，**渲染进程不碰 Node**（安全底线）。

## 三、技术选型

| 层 | 选什么 | 为什么 | 备选 |
|---|---|---|---|
| 桌面壳 | **Electron** | 纯 JS/TS，团队不用学 Rust；透明窗 + 点击穿透 API 成熟且被 BongoCat 验证过 | Tauri（包小但需 Rust） |
| 语言 | **TypeScript** | 四个人协作，类型能挡住大量低级错误 | JavaScript |
| 构建 | **electron-vite** | 主进程和渲染进程都能热更新，模板开箱即用 | 手写 Vite + electron-builder |
| 界面框架 | **无框架**（原生 DOM） | 桌宠只有一个画面，不需要路由和组件库，引入 React/Vue 是负担 | Vue 3 |
| 动画 | **精灵图（PNG 序列帧）起步**，后续可换 Live2D | 序列帧零依赖、最可控；Live2D 效果好但需要模型和 SDK | Lottie / Rive |
| 状态管理 | **自写状态机**（switch + 定时器） | 只有 4 个状态，引入 XState 是过度设计 | XState |
| 本地存储 | **electron-store** | 一个 JSON 文件搞定设置、形象列表 | 自己写 fs |
| 图片处理 | **sharp**（主进程）或 Canvas | 本地裁剪、调色、缩放 | jimp（纯 JS，免编译） |
| 音频 | **HTMLAudioElement** | 短音效足够 | howler.js |
| 打包 | **electron-builder** | 生态最成熟，出绿色版 zip 最简单 | electron-forge |

## 五、桌宠是怎么"活"起来的

### 1. 动画 = 翻页书

一组 PNG，按顺序快速播放就是动画：

```
idle_0.png → idle_1.png → idle_2.png → idle_1.png → （循环）
```

每秒 12–24 张。播放器只做一件事：**定时换图**。

### 2. 状态机 = "我现在该干嘛"

```
        点击
待机 ──────────> 点击反应 ──(播完)──> 待机
 │                                    ▲
 │ 30 秒没互动                          │
 ▼                                    │
睡觉 ────────────(被点醒)─────────────┘
```

规则只有几条：

- 待机时，隔一会儿随机播一个小动作（眨眼、晃尾）
- 被点击，播「点击反应」，播完回待机
- 被拖拽时，切到「被拎起来」的姿势
- 久未互动进入睡觉

**实现就是一个 `switch (currentState)` + 切换时的清理定时器。** 不需要框架。

### 3. 性格 = 一份配置表

加一种性格，**不改代码，只加一个配置**：

```ts
// src/shared/personalities/shy.ts
export const shy = {
  name: "害羞",
  animations: {
    idle: "shy/idle_%d.png",
    click: "shy/blush_%d.png",
    drag: "shy/fluster_%d.png",
  },
  lines: {
    click: ["……诶？", "别、别突然戳我啦", "（脸红）"],
    drag: ["要掉下去了……！"],
    idleLong: ["……你在忙吗"],
  },
  sounds: {
    click: "shy/ehh.mp3",
  },
};
```

切性格 = 换一个配置对象。动作、台词、音效**同时**跟着变，这正是问卷里 55.77% 用户抱怨「性格不稳定」的解药。

## 六、换肤的真相（必须提前对齐）

问卷里 61.54% 的人想要「上传图片生成专属外观」。但**真正的「照片 → 生成角色形象」是一个 AI 研究课题**，本地跑不动，云端跑违反隐私红线（53.85% 用户的首要顾虑）。

所以 MVP 的做法是**模板换肤**，不是 AI 生成：

```
用户选一张图
   ↓
本地提取主色调 / 纹理（sharp）
   ↓
套用到预置的 3 套基础形象模板上（换色、换花纹）
   ↓
得到 N 个变体，用户挑一个
   ↓
全程无网络
```

**诚实地说，这只能让宠物"换成你喜欢的配色"，不能"长得像你"。** 这与报告里写的风险兜底一致：「预置基础形象模板 + 上传图仅作换肤」。答辩时要讲清楚这条边界，而不是含糊过去。

## 七、五个一定会踩的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **透明窗口和点击穿透自相矛盾** | 全窗穿透后，宠物也点不到了 | 鼠标位置轮询：进入角色包围盒时关穿透，离开时开回来 |
| **用 CSS 拖拽会吞掉点击** | `-webkit-app-region: drag` 让点击事件全部失效 | 自己实现拖拽：`mousedown` 记偏移 → `mousemove` 调 `setPosition` |
| **置顶窗口抢焦点** | 一点宠物，你的代码编辑器就失焦 | `focusable: false` + `skipTaskbar: true` |
| **多显示器和缩放漂移** | 笔记本接了显示器后，宠物跑到屏幕外 | 用 `screen.getDisplayMatching` 换算坐标，别写死像素 |
| **打包后资源找不到** | dev 能跑，装完就白屏 | 路径统一走 `app.getAppPath()`，别用相对路径 |

这五条每一条都能让人卡一整天。**建议 P0-3 就把前三个验掉。**

## 八、构建顺序（对应 BACKLOG）

| 周 | 做什么 | 能看到的成果 |
|---|---|---|
| 1 | 开窗：透明 + 置顶 + 穿透 + 拖拽 | 一个能拖动的透明窗口 |
| 2 | 让它动：动画播放器 + 状态机 | 点一下有反应 |
| 3 | 有性格：配置化 + 气泡 + 托盘 + 勿扰 | 换性格像换了只宠物 |
| 4 | 能换皮：本地模板换肤 | 传张图换个颜色 |
| 5 | 能分发：打包 + 官网下载 | 别人能装上 |

## 九、为什么不用别的方案

| 方案 | 为什么不选 |
|---|---|
| Tauri | 要 Rust；WebView2 版本差异会让动画表现不可控。作为备选保留，见 `DECISIONS.md` D-004 |
| Unity / Godot | 做桌宠要自己处理透明窗、点击穿透、托盘，等于重造轮子；包体也大 |
| 纯 Win32 / WPF | 只有 Windows，团队学习成本高，且动画生态弱 |
| 网页 + 插件 | 做不到真正的桌面常驻 |
